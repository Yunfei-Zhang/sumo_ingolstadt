# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

This is a **SUMO (Simulation of Urban Mobility) scenario** for the city of Ingolstadt — not a typical software project. The "code" is mostly XML configuration and large gzipped network/route data. There is no build step, no package manager, no test framework. Work here is primarily editing `.sumocfg` configurations, swapping route/network/additional files, and running SUMO against them.

## Running simulations

SUMO 1.19.0 is the reference version (`SUMO_HOME` must be set). Two binaries are commonly used:

- `sumo -c <path-to.sumocfg>` — headless run (used in CI).
- `sumo-gui -c <path-to.sumocfg>` — interactive viewer.

Common entry points:

- [simulation/24h_sim.sumocfg](simulation/24h_sim.sumocfg) — primary 24h motorized scenario, 16.09.2020 demand.
- [simulation/24h_bicycle_sim.sumocfg](simulation/24h_bicycle_sim.sumocfg) — bicycle-only variant.
- [simulation/Ingolstadt SUMO 365/](simulation/Ingolstadt%20SUMO%20365/) — per-day configs (e.g. `2023-06-19.sumocfg`) calibrated for 9 days in summer 2023, including public-transport routes from GTFS.
- [simulation/parking_simulation/24h_parking_sim.sumocfg](simulation/parking_simulation/24h_parking_sim.sumocfg) — adds parked-vehicle layer for parked-vehicle-as-sensor experiments.

If a run is slow, drop polygons from `additional-files` (cosmetic only).

CI runs SUMO from both the Ubuntu PPA and the nightly PyPI build via [.github/workflows/linux.yml](.github/workflows/linux.yml). It runs the full `24h_sim.sumocfg` and the first hour (`-e 3600`) of `24h_bicycle_sim.sumocfg`. Any change that breaks the headless run will fail CI.

## Scenario architecture

Each `.sumocfg` is a thin wrapper that points to four kinds of files. To understand or modify a scenario, you almost always need to read the config plus its referenced files together.

| Role | Extension | What it contains |
|---|---|---|
| Network | `*.net.xml(.gz)` | Roads, lanes, junctions, traffic-light skeletons. Generated by SUMO's netconvert; treat as a binary artifact. |
| Demand / routes | `*.rou.xml(.gz)` | Vehicle/person flows and their routes. Calibrated against real-world counts and GPS traces. |
| Additionals | `*.add.xml` | Traffic-light programs (`tlLogics`), WAUT schedules, polygons, parking areas, detector outputs. Multiple are listed comma-separated under `<additional-files>`. |
| GUI settings | `gui_settings.settings.xml` | Default view/colors for `sumo-gui`. |

Two structural points that aren't obvious from a single file:

1. **Traffic lights need both a `tlLogics_*.add.xml` AND its WAUT (Wochenschaltautomatik).** Without the WAUT loaded, traffic lights don't switch correctly through the day. This is also why several days/scenarios ship duplicate-looking `*.net.xml` files with identical geometry — the embedded TL programs differ.
2. **Calibration is per-day.** The 365-style configs each load their own dated route file, TL logic, and WAUT. Don't cross-wire files across dates.

## Editing conventions

- File paths in `.sumocfg` are **relative to the config's own directory**. Moving a config requires updating its references.
- Some configs (notably under `parking_simulation/`) contain Windows-style backslash output paths like `runs\...\edgeData.xml`. These work on Windows but break on Linux/CI — convert to forward slashes when touching them.
- The network is *not* validated for pedestrian simulation (missing crossings make it disconnected). Don't enable pedestrian flows without expecting issues.
- Most large `.xml.gz` files are tracked directly (LFS was removed — see commit `7f1465b`). Avoid re-introducing LFS or rewriting these blobs casually; diffs are huge and review-hostile.
